# REQUIREMENTS — Cosmic Watch & Explorer

> **무엇을 만들고 무엇을 만들지 않는지 적는 문서다.** 기능 번호와 우선순위는 6장.
> 진행 상황은 [PLAN](PLAN.md), 화면은 [DESIGN](DESIGN.md), 왜 이 스택인지는 [decisions/](decisions/README.md).

## 1. 프로젝트 목적

NASA 및 공개 천문 데이터로 지구 근접 소행성(NEO)과 외계행성(Exoplanet) 정보를 통합 조회 · 탐색하는 웹 기반 천문 관제 · 탐색 포털이다.

- 지구 근접 소행성의 접근 정보 및 위험 여부 모니터링
- 외계행성의 다양한 조건 기반 검색
- 천체의 상세 정보 및 궤도 데이터 제공
- NEO, 지구, 외계행성의 크기 비교
- 사용자의 관심 천체 Watchlist 관리

### 1.1 용어 정의에 관한 주의

NASA API 데이터를 **주기적으로 수집 · 갱신하여 제공**하는 서비스이며, 천체를 직접 실시간 관측하는 시스템이 아니다. 문서와 포트폴리오에서 "실시간 관측 시스템"이라고 쓰지 않고 **"통합 천문 관제 · 탐색 포털"** 로 표기한다.

## 2. 프로젝트 대상 사용자

### 2.1 주요 사용자

천문학에 관심이 있는 일반 사용자. 전문 지식이 없어도 주요 정보를 쉽게 조회할 수 있어야 한다.

- 오늘 지구에 접근하는 소행성이 궁금한 경우
- 특정 외계행성을 검색해 보고 싶은 경우
- 행성 크기를 지구와 비교해 보고 싶은 경우
- 관심 있는 천체를 저장해 두고 싶은 경우

### 2.2 사용자 유형

| 사용자 유형 | 할 수 있는 것 |
|---|---|
| 비회원 | 로그인 · 회원가입만 ([decisions/0004](decisions/0004-lock-all-screens.md)) |
| 회원 | NEO · 외계행성 조회와 검색, 크기 비교, Watchlist, 마이페이지(내 정보, 이메일 · 비밀번호 변경, 탈퇴, 대시보드 표시 설정), 프로필 사진과 미니 메뉴 |
| 관리자 | Django Admin으로 데이터 관리. 별도 관리자 웹페이지는 만들지 않는다 |

> **설계 판단**: 회원 기능의 핵심 목적은 "관심 있는 천체를 저장한다" 하나다. 로그인 시스템을 과도하게 확장하지 않는다.

## 3. 서비스 범위

### 3.1 MVP 포함 범위

- **NEO**: 날짜별 조회, NASA 데이터 수집 · DB 캐싱, 위험 소행성 표시, 접근 거리 · 속도, 상세 정보, 접근 이력, 궤도 정보
- **Exoplanet**: 목록, 다중 조건 검색, 페이징, 상세 정보, 모항성 정보
- **공통**: 천체 크기 비교, 회원가입, 로그인 / 로그아웃, Watchlist

### 3.2 하지 않을 것

새 기능이 떠오르면 구현하지 않고 이 표에 먼저 적는다 ([PLAN](PLAN.md) 12.1절).

| 하지 않는 것 | 이유 |
|---|---|
| 실시간 천체 위치 추적 | NASA API 데이터만으로 현재 위치를 실시간 렌더링할 필요가 없음 |
| 3D 우주 시뮬레이션 | 프로젝트 핵심 기능이 아님 |
| 자체 궤도 계산 엔진 | NASA가 제공하는 계산 결과를 활용. 유일한 예외: 일식 · 월식의 한국 가시성 ([decisions/0010](decisions/0010-eclipse-calc-exception.md)) |
| 천문 관측 장비 연동 | 범위 외 |
| 댓글 및 소셜 기능 | 서비스 정체성과 무관 |
| 별도의 관리자 웹페이지 | Django Admin으로 대체 |
| 모바일 앱 | 범위 외 |
| 다국어 · 라이트 테마 | "관측 계기판" 콘셉트([DESIGN](DESIGN.md) 1.1절)와 우선순위가 맞지 않음 |

처음에 뺐다가 계획에 넣은 것(통합 검색, 일식 · 월식, 데스크톱 앱 등)은 6장과 [PLAN](PLAN.md) M7 · M8에 있다.

## 4. 기능 요구사항

표시할 필드는 `serializers.py`와 `frontend/src/types/api.ts`가 원본이다. 여기에는 정책만 적는다.

### 4.1 NEO 대시보드

- 조회 단위는 **하루**다. NASA NEO Feed API가 날짜 단위 조회에 맞고, 구현 난이도가 낮다.
- React에서 NASA API를 **직접 호출하지 않는다.** NASA API Key는 **백엔드에서만** 관리한다.
- 거리 · 속도 · 크기 기준으로 정렬하고, 주요 데이터를 차트로 시각화한다.

### 4.2 NEO 상세

과거 및 미래 접근 기록을 모두 조회할 수 있고, NASA / JPL 상세 페이지로 연결한다.

### 4.3 Exoplanet 카탈로그

검색 조건은 행성명 · 모항성명 · 반지름 · 질량 · 평형 온도 · 지구로부터의 거리 · 공전 주기 · 발견 연도 · 발견 방법 9개이고, 조합해서 쓴다. 검색은 Django ORM으로 **서버에서** 처리한다.

### 4.4 Exoplanet 상세

행성 정보와 모항성 정보를 함께 보여 주고, 크기 비교로 이동할 수 있다.

### 4.5 천체 크기 비교

숫자로만 보여 주지 않고 상대적인 크기를 직관적으로 이해하게 한다. 비교 대상은 지구 · NEO · Exoplanet.

NEO는 NASA API가 **최소 / 최대 추정 직경**을 주므로 단일 확정값으로 표시하지 않는다.

### 4.6 회원가입 / 로그인

사용자명 · 이메일 · 비밀번호로 가입하고 Django 인증 시스템을 쓴다. 로그인 · 회원가입 말고는 전부 인증이 필요하다.

### 4.7 Watchlist

회원은 NEO와 외계행성을 저장 · 저장 취소 · 목록 조회할 수 있고, 목록에서 상세로 이동한다. 동일 사용자가 동일 천체를 중복 저장할 수 없다.

## 5. 데이터 수집 및 캐싱 요구사항

### 5.1 NEO 데이터

NASA NEO API를 외부 데이터 소스로 쓴다. Django 백엔드에서 수집한 뒤 필요한 데이터를 MariaDB에 저장한다.

### 5.2 캐싱 전략

사용자가 조회할 때마다 NASA API를 호출하지 않는다. DB에 있으면 DB로 응답하고, 없으면 호출해서 저장한 뒤 응답한다(자세히는 [DATA_MODEL](DATA_MODEL.md) 3.7절).

기대 효과: NASA API 호출 횟수 감소, 응답 속도 개선, API 장애 시 기존 데이터 활용, API Key 보호.

## 6. 기능 우선순위

M = MVP, S = 직후, L = 나중. 어느 단계에서 하는지와 진행 상황은 [PLAN](PLAN.md)에만 적는다.

| 번호 | 기능 | 우선순위 |
|---|---|---|
| N-01 | NEO 수집 · DB 저장, 날짜별 목록 · 요약 | M |
| N-02 | NEO 상세 (궤도 · 다음 접근 · 크기), 전체 접근 기록 | M |
| N-03 | 달 거리 스케일 바, 거리-속도 산점도 | M |
| N-04 | 다음 근접 접근 카운트다운 | S |
| E-01 | 외계행성 저장, 다중 조건 검색, 페이징 · 정렬 | M |
| E-02 | 외계행성 상세, 모항성 · 형제 행성 | M |
| C-01 | 천체 크기 비교 | M |
| A-01 | 회원가입 · 로그인 · 로그아웃, 화면 · API 잠금 | M |
| W-01 | Watchlist (저장 · 삭제 · 실행 취소, 중복 방지) | M |
| A-02 | 마이페이지, 프로필 사진 · 미니 메뉴 | S |
| N-05 | 통합 검색 (Ctrl K) | S |
| N-06 | 관심 천체 접근 알림 (화면 안) | S |
| N-07 | Sentry 충돌 위험 정보 | S |
| E-03 | 외계행성 지구 유사도(ESI) 정렬 · 검색 | S |
| S-01 | 일식 · 월식 일정 (한국 가시성 중심) | S |
| E-04 | 생명 가능 지대 표시 | L |
| N-08 | 대시보드 기간 조회, 접근 기록 연표 차트 | L |
| N-09 | 이메일 알림 | L |
| D-01 | 데스크톱 앱 | L |

- **M**: 서비스 핵심 기능. 반드시 구현한다. NASA 수집과 다중 조건 검색이 빠지면 이 프로젝트는 존재 이유가 없다.
- **S**: v1.0 직후 서비스를 자라게 하는 기능.
- **L**: 하지 못해도 v1.x가 성립한다.

## 7. 비기능 요구사항

### 7.1 보안

- NASA API Key를 프론트엔드에 노출하지 않고 환경변수로 관리한다.
- 비밀번호는 평문으로 저장하지 않는다.
- 인증이 필요한 API는 인증 여부를 검증한다.

### 7.2 성능

- NEO 데이터는 DB 캐싱을 쓴다.
- Exoplanet 검색은 서버 측 페이징을 적용한다.
- 목록 API에서 불필요한 데이터를 과도하게 반환하지 않는다.

### 7.3 데이터 무결성

- PK / FK로 테이블 관계를 유지한다.
- Watchlist 중복 등록을 방지한다.
- NASA 데이터의 NULL 값을 임의의 값으로 변환하지 않는다.

### 7.4 유지보수성

Backend와 Frontend를 분리하고, 외부 NASA API 통신 로직을 비즈니스 로직과 분리한다 ([ARCHITECTURE](ARCHITECTURE.md) 1장).
