### [백엔드] 처음 조회하는 날짜가 503(UPSTREAM_ERROR) ─ 원인은 NASA가 아니라 `print()`

**증상**
대조 중 처음 조회하는 `2026-11-10`이 "NASA 데이터 서버에 연결할 수 없습니다"(503). 같은 날짜를 5초 뒤 다시 부르면 200. 같은 키로 파이썬에서 NASA를 직접 부르면 정상.

**원인**
처음엔 StrictMode의 이중 요청이 동시에 저장하다 충돌한 줄 알았다 → shell에서 스레드 2개로 재현해 보니 둘 다 `UnicodeEncodeError: 'cp949' codec can't encode character '—'`. `fetch_feed` 끝의 `print("… 저장 완료 — …")`의 "—"가 원인. Windows에서 서버 출력이 화면이 아니라 **파이프**(미리보기 서버·백그라운드·배포 로그)면 인코딩이 cp949라 그 글자를 못 쓴다. 저장은 다 끝난 뒤라 다음 요청은 캐시로 200 ─ 그래서 "한 번 실패하고 저절로 낫는" 것처럼 보였다. 터미널에서 직접 runserver를 켜면(콘솔은 유니코드 OK) 재현되지 않아 지금까지 몰랐다.

**해결**
`services/nasa_neo.py`의 print 3곳 → `logging`(출력에 실패해도 요청을 안 깨뜨림), "—"·"―" → "-". `settings.LOGGING`에 `apps` 로거 INFO를 콘솔로. 미리보기 서버에서 처음 조회 `2026-11-12` 첫 요청 200 확인.

**배운 것**
- 뷰의 `except Exception: raise UpstreamError()`는 "NASA 탓"이 아닌 오류까지 NASA 탓으로 바꾼다. 503의 진짜 원인은 `from exc`로 이어진 원래 예외를 봐야 안다 ─ 이번엔 스레드 재현으로 꺼냈다.
- 요청 처리 중엔 `print` 금지, `logging`만. 미리보기 서버 로그의 한글이 깨져 보이는 건(cp949로 쓴 걸 UTF-8로 읽음) 표시 문제일 뿐 요청엔 영향 없다.

### [백엔드] 카운트다운 이름을 누르면 "찾는 항목이 없습니다" ─ JPL과 NeoWs의 ID 번호가 다르다

**증상** 카운트다운의 (2018 GS1) 링크 → `/neo/50802451` → NOT_FOUND. 같은 날 대시보드 목록의 (2018 GS1)은 잘 열림.
**원인** 처음엔 링크 ID를 JPL SBDB API(`sbdb.api?sstr=2018 GS1` → `spkid`)로 받았다. SBDB는 새 번호 **50802451**, 우리 DB(NeoWs feed)는 옛 번호 **3802428**. NeoWs 자체는 두 번호 다 받아 주지만(10-28 직접 확인), 우리 상세 API는 "DB에 없는 ID면 NASA를 부르지 않고 404"라서 열리지 않았다. 백엔드 테스트는 가짜 SBDB가 준 ID를 그대로 믿어서 못 잡았다.
**해결** SBDB 호출을 없애고, JPL `fullname`("(2018 GS1)", 앞 공백 제거)과 NeoWs `name`이 같은 모양인 걸 이용해 **우리 DB에서 이름으로** `nasa_id`를 찾는다. 없으면 `null` + `approach_date` → 화면은 "그날 목록 보기"(거기서 NASA 목록을 받아 오면 상세도 열린다). 이름 매칭 테스트 추가.
**배운 것** 같은 기관(NASA/JPL)이라도 서비스마다 ID 체계가 다를 수 있다. "ID를 받았다"가 아니라 "그 ID로 우리 화면이 열린다"까지 실제로 눌러 봐야 한다 ─ 가짜 응답 테스트는 내가 믿은 가정을 그대로 통과시킨다.

### [환경] 환경변수 이름 충돌 ─ `DEBUG=pw:webserver`가 Django를 배포 모드로 켰다

**증상** E2E 백엔드 로그를 보려고 `DEBUG=pw:webserver npx playwright test`로 실행하자 백엔드가 `CommandError: You must set settings.ALLOWED_HOSTS if DEBUG is False.`로 안 켜짐.
**원인** Playwright는 자기 환경변수를 서버 프로세스에 그대로 물려준다(`env: {...process.env}`). Django `settings.py`는 `DEBUG = os.getenv('DEBUG', 'True') == 'True'` ─ `"pw:webserver"`는 `"True"`가 아니라서 DEBUG=False(배포 모드)가 됐다. 같은 이름 `DEBUG`를 두 도구가 서로 다른 뜻으로 쓴 것.
**해결** `playwright.config.ts` 백엔드 env에 `DEBUG: "True"`를 직접 넣음.
**배운 것** 자식 프로세스에 환경변수를 통째로 넘길 땐, 그 프로그램이 읽는 이름(DEBUG·DB_NAME 등)은 직접 고정한다. 배포(M6)에서 DEBUG를 환경변수로 나눌 때도 같은 함정 ─ 이름을 `DJANGO_DEBUG`처럼 구체적으로 바꾸는 것도 검토.

### [프론트엔드] 탈퇴 후 `/login?bye=1`이 아니라 `/login?next=/account`로 감

**증상**
탈퇴 성공 뒤 `navigate("/login?bye=1")`와 `updateUser(null)`을 같은 순간에 불렀는데, 도착한 주소는 `/login?next=%2Faccount`, 삭제 안내도 안 뜸.
**원인**
사전 검증에선 "같은 순간에 부르면 React가 한 번에 그린다(배치)"고 봤다. 그런데 React Router는 주소 이동을 **낮은 우선순위(transition)**로 처리한다 → 로그인 상태 지우기가 먼저 그려지고, 그 화면(아직 `/account`)의 문지기 ProtectedRoute가 `/login?next=/account`로 보냈다. 10-27 로그아웃 때 본 순서 문제와 같은 뿌리.
**해결**
`window.location.replace("/login?bye=1")` ─ 페이지를 새로 연다. 서버 세션은 이미 지워져 비로그인으로 시작하고, 메모리에 남은 예전 계정 정보도 사라진다.
**배운 것**
"상태 바꾸기 + 주소 이동"을 한 번에 그려질 거라 가정하지 말 것 ─ 라우터의 이동은 우선순위가 다르다. 계정이 통째로 사라지는 순간처럼 앱 전체를 리셋해야 할 땐 새로 여는 게 가장 단순하고 확실하다.

### [인증] 브라우저를 닫았다 켜도 로그인 상태가 남음 (사용자 요청)

**원인** Django 기본값 `SESSION_COOKIE_AGE` 2주 + `SESSION_EXPIRE_AT_BROWSER_CLOSE = False` → `sessionid` 쿠키에 2주 뒤 만료일이 붙어 브라우저를 껐다 켜도 남았다.
**해결** `SESSION_EXPIRE_AT_BROWSER_CLOSE = True` ─ 만료일 없는 세션 쿠키로. 테스트 `test_login_cookie_ends_with_browser`(False로 되돌리면 `'Wed, 11 Nov 2026 …' != ''`로 실패하는 것 확인). 실제 응답 헤더에서 Expires가 사라진 것 확인.
**주의** ① 이미 로그인돼 있던 브라우저는 예전 2주짜리 쿠키라 한 번 로그아웃 → 로그인해야 적용 ② 크롬·엣지 "시작 시 이전 세션 계속하기"는 세션 쿠키도 되살린다 ③ 탭만 닫으면 유지(브라우저 전체를 닫아야 함). 서버 쪽 세션 행은 2주 뒤 만료.

### [보안] 실패 로그에 NASA API 키가 통째로 찍힐 뻔 (가짜 키 실험 중 발견)

**증상**
결정 A 확인용으로 서버를 가짜 키(환경변수만, `.env` 그대로)로 띄우고 실패 로그를 `exc_info=True`로 남겼더니 로그에 `requests.exceptions.HTTPError: 403 … for url: https://api.nasa.gov/neo/rest/v1/neo/3701679?api_key=INVALID_TEST_KEY`.
**원인**
requests의 오류 문구에는 요청 URL이 통째로 들어간다. NASA 키는 쿼리스트링(`?api_key=`)으로 보내므로 진짜 키였다면 그대로 로그 파일에 남았다. `raise UpstreamError() from exc`처럼 원래 예외를 이어 붙여도 DEBUG 오류 화면·로그 체인에 같은 문구가 실린다.
**해결**
서비스의 `NasaUnavailable`은 "HTTP 403"·"ConnectTimeout"처럼 종류만 담고 원래 예외는 `from None`으로 끊는다. 뷰는 트레이스백 없이 그 문구만 기록. 테스트 `test_failure_log_never_contains_api_key`(오류 문구에 `api_key=SECRET123`을 넣고 로그에 없는지 확인).
**배운 것**
키를 URL로 보내는 API는 "오류 메시지 = 키 노출 경로"다. 로그는 대화·커밋과 같은 급으로 다룬다(CLAUDE.md 2.2 "키 값을 로그에 남기지 않는다"). 가짜 키로 실험한 덕에 진짜 키가 새기 전에 잡았다.

### [설계] 배포 플랫폼 결정 ─ AWS Lightsail **시드니** (서울 아님), 도메인은 외부 업체 (사용자 결정)

**경과** 처음 추천은 Lightsail 서울 + Route 53 도메인이었는데, 실제로 해 보니 계정에서 세 번 막혔다.
- **Route 53 도메인 등록 실패**: Lightsail 화면은 `.dev`를 안 받고, Route 53 콘솔에서 `sagming.com`을 신청하자 "등록을 마칠 수 없음 ─ Support 문의"로 실패(청구 0)
- **서울 리전 차단**: Lightsail 화면이 403 ─ 오류 문구가 `a service control policy explicitly denies the action`. 쓰던 계정이 AWS 새 가입 방식("프로젝트" 계정 ─ AWS가 관리하는 조직 소속, 리전 1개 + 지출 한도)이라 **시드니만 허용**. 다른 리전은 "고급 기능 활성화"(되돌릴 수 없음, 지출 한도 삭제, 조직 관리자 + SCP 직접 수정 필요)를 해야 열린다
- **예전 일반 계정 발견**: 같은 이메일로 가입이 덜 끝난 일반 계정이 있었다 → 가입을 마치니 "이미 등록된 고객이라 무료 플랜·신규 크레딧 대상 아님" → 유료 플랜(크레딧 없음, 지출 강제 상한 없음)

**결정 (사용자)**: 프로젝트 계정에서 **Lightsail 시드니**로 배포.
| | 프로젝트 계정 · 시드니 ✅ | 일반 계정 · 서울 |
|---|---|---|
| 비용 | 크레딧 $120 (몇 달 거의 무료) | 처음부터 카드 결제 |
| 안전장치 | **지출 한도 $30 강제 상한** | 알림(Budgets)만 |
| 제약 | 시드니만, 도메인 등록 불가 | 없음 |
| 한국에서 속도 | 조금 느림(왕복 0.1초대) | 빠름 |
- 처음 하는 배포라 "실수해도 상한에서 멈추는" 쪽을 고름. 서울이 필요해지면 백업 → 새 서버 복원으로 옮긴다
- 도메인 `sagming.com`은 Cloudflare·Porkbun 같은 외부 업체에서 사서 DNS만 Lightsail 고정 IP로 연결 (AWS 계정 제약과 무관, Route 53 호스팅 영역 월 0.5달러도 없음)
- 일반 계정은 비워 둔다(리소스 0 = 비용 0). 루트 MFA만 등록. 두 계정에 서버를 나눠 만들지 않는다
- **같은 날 추가**: 사용자가 억울한 사정(모르고 한 가입 순서)을 AWS Support에 문의(계정 및 결제 · Free Tier) ─ 신규 혜택을 일반 계정에 적용하거나 크레딧을 옮겨 달라는 요청. **답이 올 때까지 서버 생성 보류**: 승인되면 일반 계정·서울, 거절되면 위 결정대로 시드니

**배운 것** 클라우드 계정은 "가입했다 = 다 쓸 수 있다"가 아니다. 리전·서비스 제한, 지출 한도, 신규 혜택 조건이 계정 종류마다 다르다 ─ 서버를 고르기 전에 그 계정에서 **화면이 열리는지부터** 확인한다. 오류 문구의 "service control policy"는 계정 안 권한으로는 못 푸는, 조직 단위의 거부라는 신호다.
