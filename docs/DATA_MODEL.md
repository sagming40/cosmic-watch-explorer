# DATA_MODEL — Cosmic Watch & Explorer

> **무엇을 어디에 왜 저장하는지 적는 문서다.** DBMS는 MariaDB (InnoDB / utf8mb4).
> 컬럼 · 타입 · 제약은 코드가 원본이다: `backend/apps/*/models.py`, `backend/apps/*/migrations/`. 응답 모양은 [ARCHITECTURE](ARCHITECTURE.md) 3장.

## 1. 설계 원칙

### 1.1 NASA 원본 데이터를 훼손하지 않는다

NASA가 `null`을 주는 필드는 DB에도 `NULL`로 저장한다. `0`이나 `-1` 같은 임의의 값으로 치환하지 않는다.

> **이유**: 외계행성 데이터에서 `pl_rade = null`은 "반지름이 0이다"가 아니라 **"아직 측정되지 않았다"** 는 뜻이다. 이걸 0으로 바꾸면 "지구보다 작은 행성 검색"에 측정 안 된 행성이 전부 딸려 나온다.

### 1.2 단위를 컬럼명에 명시한다

`diameter`가 아니라 `diameter_min_m`, `velocity`가 아니라 `velocity_km_s`로 쓴다. 나중에 코드에서 단위를 헷갈릴 여지를 없앤다.

### 1.3 시간은 UTC임을 컬럼명에 표시한다

MariaDB의 `DATETIME` 타입에는 타임존 정보가 없다. 따라서 컬럼명에 `_utc`를 붙인다 (`approach_datetime_utc`, `orbit_determination_datetime_utc`).

### 1.4 외부 ID와 내부 ID를 분리한다

NASA가 주는 ID(`2357621`)를 그대로 PK로 쓰지 않는다. 내부 PK는 따로 두고, NASA ID는 `nasa_id UNIQUE`로 저장한다.

> **이유**: 외부 시스템의 ID 체계가 바뀌어도 우리 DB의 관계(FK)가 깨지지 않는다.

### 1.5 테이블은 마이그레이션으로만 만든다

실제 테이블 생성은 `python manage.py migrate`로 한다. DDL을 손으로 실행하고 Django 모델도 만들면 두 정의가 어긋난다. HeidiSQL은 결과를 눈으로 확인하고 데이터를 조회하는 용도로만 쓴다.

## 2. 전체 관계도

앱은 성격으로 나눈다: `astronomy`(NASA 사실 데이터) / `watchlist`(사용자가 만든 데이터) / `accounts`(인증 · 표시 설정 · 프로필 사진).

```text
                        ┌─────────────────┐
                        │   auth_user     │ ──1:1── user_preference
                        │  (Django 기본)  │ ──1:1── user_avatar
                        └────────┬────────┘
                                 │
                  ┌──────────────┴──────────────┐
                 1:N                           1:N
                  │                             │
                  ▼                             ▼
        ┌───────────────────┐       ┌─────────────────────────┐
        │  neo_watchlist    │       │  exoplanet_watchlist    │
        └─────────┬─────────┘       └────────────┬────────────┘
                 N:1                            N:1
                  │                              │
                  ▼                              ▼
            ┌───────────┐                  ┌─────────────┐
            │    neo    │                  │  exoplanet  │
            └─────┬─────┘                  └──────┬──────┘
                  │                               │
        ┌─────────┴─────────┐                    N:1
       1:N                 1:1                    │
        │                   │                     ▼
        ▼                   ▼               ┌─────────────┐
┌────────────────┐  ┌──────────────┐        │  host_star  │
│ close_approach │  │ orbital_data │        └─────────────┘
└────────────────┘  └──────────────┘

        ┌──────────────────┐
        │  neo_fetch_log   │   ← 독립 테이블 (수집 이력 관리)
        └──────────────────┘
```

### 2.1 관계 요약

| 관계 | 형태 | 설명 |
|---|---|---|
| neo → close_approach | 1:N | 하나의 소행성은 여러 번 지구에 접근한다 |
| neo → orbital_data | 1:1 | 소행성 하나당 최신 궤도 데이터 하나만 저장한다 |
| host_star → exoplanet | 1:N | 하나의 항성은 여러 행성을 거느린다 |
| user → neo_watchlist | 1:N | 사용자는 여러 NEO를 북마크한다 |
| user → exoplanet_watchlist | 1:N | 사용자는 여러 외계행성을 북마크한다 |
| user → user_preference | 1:1 | 표시 설정. 처음 바꿀 때 행을 만든다 |
| user → user_avatar | 1:1 | 프로필 사진 한 장 |

사용자 쪽 테이블은 전부 `ON DELETE CASCADE`다. 탈퇴하면 같이 지워진다.

## 3. 테이블별 설계 이유

### 3.1 `neo` — 소행성 기본 정보

소행성 자체의 **변하지 않는 속성**을 담는다. 접근 기록이나 궤도 데이터는 별도 테이블로 분리한다.

**직경을 두 컬럼으로 나눈 이유**: NASA는 소행성의 정확한 직경을 알지 못한다. 밝기로 추정하기 때문에 **범위**로 준다. 평균 내서 하나로 합치면 원본 정보가 사라진다. 크기 비교 화면에서 "이 소행성은 455m ~ 1,018m 사이"라고 범위로 보여 주는 게 정직하다.

### 3.2 `close_approach` — 지구 접근 기록

`UNIQUE (neo_id, approach_datetime_utc, orbiting_body)` ─ NASA API를 여러 번 수집해도 같은 접근 기록이 중복 저장되지 않는다.

**`approach_date`와 `approach_datetime_utc`를 둘 다 두는 이유**: `DATETIME` 하나만 있어도 날짜 검색은 가능하지만 `DATE(approach_datetime_utc) = '2026-08-21'`처럼 컬럼에 함수를 씌우면 **인덱스가 무용지물이 된다.** 도서관에서 "제목이 ㄱ으로 시작하는 책"은 색인으로 바로 찾지만, "제목의 글자 수를 세어서 5글자인 책"은 전부 뒤져야 하는 것과 같다. NEO 대시보드의 핵심 쿼리가 날짜 조회이므로 이 중복은 정당하다.

### 3.3 `orbital_data` — 궤도 정보

**`neo_id`에 UNIQUE를 거는 이유**: NASA는 관측이 쌓일 때마다 궤도를 다시 계산한다. 우리 서비스는 **최신 궤도 하나만** 보여 주면 충분하다. 갱신할 때 새 행을 추가하지 않고 덮어써서, 데이터가 무한히 쌓이는 걸 막는다.

이 행의 존재 자체가 "NASA Lookup을 이미 불렀다"는 표시이기도 하다(소행성 상세를 처음 열 때 수집).

### 3.4 `host_star` — 모항성

**거리를 `host_star`에 둔 이유**: 같은 항성계의 행성들은 **지구로부터 같은 거리**에 있다. 행성마다 거리를 저장하면 같은 값이 반복 저장되고, 수정할 때 일부만 고쳐져 어긋날 수 있다.

> **주의 — 단위 문제**: 검색 조건은 "거리 ≤ 100 광년(ly)"인데 NASA가 주는 값은 **파섹(pc)** 이다 (`1 pc = 3.26156 ly`). **저장은 파섹, 화면 표시는 광년**으로 하고 변환은 백엔드(`units.py`)에서 처리한다. DB에 두 단위를 모두 저장하지 않는다.

### 3.5 `exoplanet` — 외계행성

**NULL 허용이 핵심이다.** 실제 NASA Exoplanet Archive 응답에는 측정값이 비어 있는 행성이 매우 많다(`radius_earth IS NULL` 1,612건, 2026-08-31 실측). `NOT NULL`을 걸면 데이터의 상당수를 아예 저장하지 못한다.

수집 출처는 `ps` 테이블의 `default_flag = 1` 행이다. 같은 행성이 여러 논문 값으로 중복 등록돼 있어 대표 판본만 고른다.

### 3.6 `neo_watchlist` / `exoplanet_watchlist`

`UNIQUE (user_id, neo_id)`, `UNIQUE (user_id, exoplanet_id)` ─ 중복 북마크를 **DB 레벨에서** 차단한다. 애플리케이션 코드에서 "이미 있나 확인 후 저장"하는 방식은 동시에 두 번 요청이 들어오면 뚫린다.

### 3.7 `neo_fetch_log` — 수집 이력

**왜 필요한가**: "DB에 데이터가 없다"는 두 가지 상황을 구분해야 한다.

1. 아직 그 날짜를 수집하지 않았다 → NASA API를 호출해야 함
2. 수집은 했는데 그날 접근하는 소행성이 **0개**였다 → 호출할 필요 없음

이 구분이 없으면 소행성이 없는 날짜를 조회할 때마다 매번 NASA API를 호출한다. 편의점 재고 확인과 같다. 선반이 비어 있을 때 "아직 발주를 안 넣었다"와 "발주했는데 그 상품이 원래 안 들어오는 날이다"는 완전히 다른 상황이다. `neo_fetch_log`는 **발주 장부** 역할을 한다.

```text
사용자가 2026-08-21 요청
        ↓
neo_fetch_log에 fetch_date = '2026-08-21' 행이 있는가?
   ┌────────┴────────┐
  있음               없음
   ↓                  ↓
close_approach     NASA API 호출
에서 조회               ↓
(0건이어도 정상)    데이터 저장
                       ↓
                  fetch_log에 기록
                       ↓
                    응답
```

`fetched_at`은 **마지막으로 받은 시각**이다. 오늘 이후 날짜는 24시간 지나면 다시 받고([ARCHITECTURE](ARCHITECTURE.md) 4.2절) 이 값도 새로 찍는다. 모델이 `auto_now_add`라 재수집 때는 서비스가 직접 갱신한다.

### 3.8 `user_preference` — 사용자 표시 설정

행은 사용자가 설정을 처음 바꿀 때 만든다. 없으면 기본값과 같다고 본다 ─ 기존 사용자용 데이터 마이그레이션이 필요 없다. 설정을 서버에 두는 이유는 사용자가 여러 기기에서 쓰기 때문이다.

### 3.9 `user_avatar` — 프로필 사진

서버가 다시 만든 256×256 WebP 바이트(약 2 ~ 30KB)를 넣는다. 원본은 저장하지 않는다. `updated_at`은 주소 `?v=`에 넣어 브라우저 캐시를 깬다.

- **파일(MEDIA)이 아니라 DB에 두는 이유**: 무료 배포 서비스는 서버를 다시 켜면 디스크에 쓴 파일이 사라진다. 작은 사진 한 장이라 DB가 더 단순하고 배포에도 안전하다. 사진이 커지거나 여러 장이 되면 외부 저장소(S3 등)로 옮긴다.
- **user_preference와 나눈 이유**: `/me/`가 요청마다 설정을 읽는데, 그때마다 사진 바이트까지 끌고 오지 않게.

### 3.10 `auth_user.email` UNIQUE

Django `User.email`은 기본적으로 unique가 아니다. 커스텀 User로 갈아끼우려면 마이그레이션 전체를 폐기해야 해서, `accounts 0001`에서 `RunSQL`로 UNIQUE 인덱스(`uk_auth_user_email`)만 추가했다.

감수할 것: 빈 이메일(`''`)도 값이라 "이메일 없는 계정"은 전체에서 1개만 된다. `createsuperuser` 때 이메일을 꼭 입력한다.

## 4. 인덱스 전략

인덱스는 **책 뒤의 찾아보기**와 같다. 없어도 내용은 다 있지만, 원하는 항목을 찾으려면 첫 페이지부터 전부 넘겨야 한다. 실제 목록은 `models.py`의 `db_index` · `unique`가 원본이다.

### 4.1 무엇을 왜 걸었나

| 인덱스 | 이유 |
|---|---|
| **`close_approach.approach_date`** | **대시보드 핵심 쿼리** |
| **`host_star.distance_pc`** | **거리 조건 검색** |
| **`exoplanet.radius_earth`** | **크기 조건 검색** |
| **`exoplanet.mass_earth`** | **질량 조건 검색** |
| **`exoplanet.discovery_year`** | **발견 연도 검색** |
| `neo.is_hazardous`, `orbital_data.orbit_class_type`, `exoplanet.discovery_method` | 분류 필터 |
| `close_approach.miss_distance_km` | "가장 가까운 NEO" 정렬 |

### 4.2 외계행성 검색 인덱스 4개가 특히 중요한 이유

다중 조건 검색이 이 프로젝트에서 백엔드 실력을 보여 주는 핵심 기능이다. 검색 조건이 9개인데 인덱스가 없으면 조건을 조합할 때마다 전체 테이블을 스캔한다. 외계행성 데이터는 6,000건 이상이므로 체감할 수 있는 수준으로 느려진다.

### 4.3 인덱스를 남발하지 않는 이유

인덱스는 조회를 빠르게 하는 대신 **저장을 느리게** 만든다. 책에 찾아보기를 만들면 새 내용을 추가할 때마다 찾아보기도 갱신해야 하는 것과 같다. 실제로 검색 조건으로 쓰이는 컬럼에만 건다.

## 5. NASA 데이터를 저장할 때

필드 매핑은 코드가 원본이다: `services/nasa_neo.py`(NeoWs Feed · Lookup), `services/exoplanet_archive.py`(Exoplanet Archive `ps` 테이블). 코드만 봐서는 모르는 주의점만 적는다.

- NASA는 숫자 값을 **문자열**로 준다(`"18.83"`). 저장 전에 형변환한다.
- 접근 시각은 `"2026-Aug-21 03:16"` 형식, 궤도 결정 시각은 `"2021-05-24 17:55:05"` 형식이라 파서가 따로다.
- **수집 순서**: `host_star`를 먼저 저장(또는 조회)한 뒤 `exoplanet`을 저장한다. FK가 걸려 있어 순서를 지키지 않으면 실패한다.
- 관측값(`neo`, `orbital_data`, `host_star`, `exoplanet`, `close_approach`)은 `update_or_create`로 저장해 NASA가 고친 값을 반영한다.
