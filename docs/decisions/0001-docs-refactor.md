# 0001. 문서를 전역 문서 체계에 맞춰 재정비

- 상태: 확정
- 날짜: 2026-11-04

## 맥락

`docs/`가 번호 붙은 문서 5개(`01` ~ `05`)와 DEVLOG 1,761줄이었다. 문서마다 버전 표 · 변경 이력이 있었고, 02에는 코드와 같은 DDL · Django 모델이, 04에는 엔드포인트 요청 · 응답 예시가 그대로 있었다. 구현이 바뀔 때마다 여러 곳을 고쳐야 했고, 실제로 어긋나 있었다(04 머리의 최종 수정일은 09-10인데 변경 이력은 10-28까지, 02의 관계도에 `user_preference` · `user_avatar`가 없음, 03에 없어진 컴포넌트 목록). 코드 주석 230줄(87개 파일)이 이 번호들을 부르고 있었다.

## 결정

전역 `CLAUDE.md` "문서 체계" 절을 그대로 따른다.

- 이름: `01` → REQUIREMENTS, `02` → DATA_MODEL, `03` → DESIGN, `05` → PLAN, 04는 ARCHITECTURE로 나눈다. 대응표는 [archive/README](../archive/README.md).
- **절 번호는 유지한다.** 코드 주석과 옛 기록이 절 번호로 부르기 때문이다.
- 코드가 원본인 것(컬럼 · DDL · 모델 · 필드 매핑 · 엔드포인트 · 컴포넌트 목록)은 문서에서 빼고 원본을 가리킨다.
- 엔드포인트 원본은 지금 `urls.py` · `serializers.py` · `frontend/src/types/api.ts` · `tests.py`다. M6에서 `drf-spectacular`를 붙이면 `/api/docs`로 바꾼다. 그때까지 옛 예시는 `archive/API_SPEC_old.md`에서 볼 수 있다.
- 버전 표 · 변경 이력은 없애고 `archive/CHANGELOG_old_docs.md`로 옮긴다. 앞으로는 git과 `decisions/` · DEVLOG `[설계]`가 원본이다.
- 끝난 단계는 archive로: DEVLOG M0 ~ M4, PLAN M0 ~ M5.
- 코드 주석의 옛 문서 번호는 새 이름으로 일괄 치환한다(주석만 바꾸는 커밋 하나).
- **`mockups/`는 지금 README만 두고, 실제 목업은 M6의 마지막 작업으로 만든다**(사용자 결정). 다 끝나야 M7로 넘어간다. 이미 구현된 화면이라 지금 그려도 결정에 쓰이지 않고, 배포를 먼저 끝내면 배포 뒤 화면까지 반영할 수 있다.

## 검토한 대안

- **주석은 그대로 두고 대응표만 둔다**: 코드를 안 건드리지만 주석을 읽을 때마다 표를 찾아야 한다. 전역 규칙("번호를 바꾸면 부르는 자리도 고친다")과도 어긋나 기각.
- **옛 문서 5개를 통째로 archive로**: 손 놓았던 레포에 쓰는 방식이다. 이 레포는 살아 있고, 그대로 옮기면 01 · 02 · 03 · 05의 git 이력이 끊겨 기각. 04만 내용이 나뉘므로 통째로 보관한다.
- **`drf-spectacular`를 먼저 붙이고 04를 지운다**: 새 의존성과 코드 변경이 들어와 문서 작업 범위를 넘는다. M6 할 일로 그대로 둔다.

## 감수할 것

- 엔드포인트 예시가 Swagger가 생길 때까지 고쳐지지 않는 옛 문서에만 있다. 어긋나면 코드가 맞다.
- 옛 기록(archive, DEVLOG 10-28 블록)에는 옛 번호가 그대로 남아 대응표를 봐야 한다.
- 목업이 없는 기간이 M6 끝까지 이어진다. 그동안 화면 기준은 DESIGN과 구현이다.
